# Bounded durable operational history (design, 2026-10-23)

Status: schema 48 task/action retention is built, installed and has passed controlled native acceptance. See `2026-10-23-schema48-acceptance.md` for final evidence, superseding source-stage deployment statements below. This covers motivation update receipts, NPC tasks, and NPC actions in `PeopleOfTheIliacBay.Core`. The experience inbox remains unbounded. Conversation archive aging and autobiographical memory compaction remain separate and deferred.

### Schema 48 source adjustment (not installed)

The source implementation now includes terminal task/action group pruning and source-classified admission. Conversation operations use deterministic IDs from the save scope, person, turn ordinal and operation kind, protected by the existing durable conversation cursor and live capabilities. Healthcare preserves its episode/attempt task ID; task steps preserve their parent task ID and step index. A new global issuance serial is not used. Generic new admissions are closed; previously accepted legacy rows remain executable.

Maintenance rotates through append-order candidates. Recent-window eligibility is ranked by terminal `UpdatedAt`, with ordinal ID as a deterministic tie-break. It does not promise globally oldest-first selection. Normal maintenance protects the latest eight terminal tasks and 32 standalone terminal actions per person and retains younger-than-30-day rows. At hard capacity, targeted cleanup may remove younger settled rows and rows inside those recent windows. Future-dated rows and live dependency pins remain protected. Task capacity only reclaims task groups; action capacity only reclaims groups containing actions or standalone actions.

Candidate examination and publication-group counts are bounded, but total work is not proportional to the candidate budget. Each call scans task/action references. On publication, the store first validates selected task/action payloads, makes a shallow `WorldState` shell with detached task/action lists and individually validated motivation rows, removes only selected rows and orphan goal-origin anchors, and performs **one** full `CopyValidated` before publishing the three owned ledgers. A failed validation leaves live ledgers unchanged. Result counters expose reference scans and full validations; four examined candidates must not be described as four total rows of work. Ordinary sweep progress survives unrelated revision changes, while pressure coverage resets when its sources change.

The source-side performance regression measures 20 real four-candidate/one-publication calls per world, with 165 terminal tasks and 1,650 actions owned by a late-listed resident. At 623 residents (63 personality profiles, 25 memory journals), two runs report publication p50 **2.242/1.846 ms**, p95 **10.612/11.145 ms**, and maximum **17.125/16.678 ms**. At 3,035 residents (304 profiles, 122 journals), p50 is **9.681/8.476 ms**, p95 **12.620/10.425 ms**, and maximum **14.064/10.674 ms**. Idle four-candidate p95 is **0.278 ms or less**, but isolated idle maxima reached **17.906/16.722 ms** in the larger world. A per-validation known-owner membership cache in task/action copy avoids repeated full-population identity scans. These timings predate the small selected-payload preflight added after independent review; no new performance run has measured that final guard. The JSON `IncludeFields` save-graph proxy is about **2.07/2.94 MB** before pruning; it is not a native FullSerializer byte count. These CPU measurements do not establish native frame pacing or a hard 16.7-ms guarantee.

The source runtime invokes projection, lodging retirement and maintenance every two real seconds only while gameplay is ready and conversation is closed. At an actual hard cap, admission performs a finite targeted sweep before rejecting pinned capacity. Rejected invalid sources or consent do not trigger cleanup. Source regressions cover failed-validation immutability, detached snapshots and malformed selected payloads. See the current implementation plan for verified test checkpoints; **schema 47 remains the installed package**. Schema-48 package installation and native acceptance have not been established by these Core measurements.

Implementation note: the motivation implementation uses a 256-receipt tail plus exact latest-row anchors. Goal-origin anchors are also retained while a tail continuation receipt references the origin; this keeps tail validation complete as the origin crosses the window boundary. The generic store commit rejects all unclassified schema-47 updates. Native health and safety use exact source checks and durable cursors; the general one-use issuance token and operation-ID serial described below are future producer work, not implemented motivation APIs. Schema-46 migration compacts only the motivation receipt window immediately, preserving all needed anchors and every task/action row; the later “no opportunistic prune” rule applies to task/action effect detail. Neither total save history nor the experience inbox is bounded by this phase.

Current-row validation also binds native Health rows to their per-kind last accepted vitals revision and native Safety rows to the last-started episode digest plus its active/closed phase. This rejects a saved older row paired with a copied, historically genuine compact anchor while the independent source cursor remains current. A schema-46 Safety row whose incident is no longer retained migrates its digest and phase, but keeps an unknown serial at zero; the missing incident cannot pass the live-object authority check, while a newly recorded generation remains admissible. These consistency checks do not authenticate a save against an attacker who coordinates arbitrary rewrites of all independent authority fields. Protecting externally modified save bytes would require a separate trusted integrity boundary.

Schema 46 integration constraint: accepted goal receipts now carry both `GoalGenerationOrigin` and `GoalStartRevision`. Retention must preserve proof that an origin actually began the episode, not merely that some receipt mentioned the goal. The latest goal receipt also prevents rewinding the current goal to an older valid lifetime. Preserve both invariants in anchors and migration; existing regression cases reject fabricated mid-episode origins and lifetime rewind. Healthcare now has a combined acceptance/binding operation, so its prevalidated care transition and admitted task must remain pinned together.

Before implementing the proposed issuance protocol, prove source-level replay prevention as well as token replay prevention. Reissuing a fresh serial for already-applied source evidence must not make the old effect admissible again. A consumed live token alone does not establish that property. Native source revision/episode checks and durable finite source cursors need explicit tests across retention, restore and branches.

## Problem and current contract

The present caps count all historical work, not just live work. `NpcMotivationState` v1 requires `AcceptedUpdates.Count == Revision`, enforces `Revision <= 4096`, and validates every current need/goal/priority row against the receipt at its `StateRevision`. `NpcHealthNeedLifecycle` and `NpcNativeSafetyGoalLifecycle` stop at that revision cap. `NpcTaskStore` rejects new work at 1,000 saved tasks; `NpcActions` rejects it at 10,000 saved actions. Their save-copy validators enforce the same limits. Thus a valid long-running save eventually loses the ability to accept a new health update, task, or action.

These rows carry authority. Task steps use action IDs exactly `task.Id + ":step:" + index`; `CopyNpcTasks` validates their target, phase, and completed effect. An acting health-care row points to its task. A health-lodging booking can also point to the task. `NpcTreatmentRecall` reads completed treatment actions and their task/purchase links. Completed item-transfer and interaction actions may still need projection into the experience inbox or conversation memory. `LatestNpcAction` currently depends on list order. A simple trim of old rows would break one or more of these contracts.

## Chosen model

Use a rolling **operational window** plus small, typed durable outcome records. Keep active work and every live reference exactly. Compact only terminal task/action groups whose downstream effects are settled. Retain a recent bounded window for diagnostics and recent recall. Reject stale proposals using issued capabilities and monotonic save-local IDs, not the continued presence of every old row.

The window is a storage policy, not a loss of current state. Inventory, vitals, care state, lodging/payment state, relationship state, motivation row state, conversation archive entries, and accepted experience outcomes remain owned by their existing ledgers. A compact operational outcome may describe only an effect that these authorities already confirm. It cannot itself authorize a payment, transfer, treatment, goal completion, or dialogue claim.

The source policy retains at most the latest 256 motivation receipts per person and protects the eight most recently completed terminal tasks and 32 standalone terminal actions per person during normal maintenance. Keep task-step actions as a group with their task while that task stays detailed. Apply the existing 1,000 task and 10,000 action global ceilings to **retained detailed rows**, after a pruning attempt; terminal rows older than 30 native game days become normal eviction candidates. At pressure, the rotating sweep may evict a younger eligible terminal group or a row inside the recent window. Exact active and pinned rows never evict. If pinned rows alone fill a ceiling, reject new work with a distinct capacity reason and telemetry; do not discard an active obligation. This makes the ceilings bounded safety limits rather than lifetime quotas. Motivation receipt count stays within 256 after each accepted update, independent of its ever-increasing `long Revision`.

The proposed numeric window is a policy choice, not a claim that the current save has these distributions. Multi-year tests must prove that ordinary gameplay can continue after many times the old caps and that pinned-only capacity failure is explicit.

## Motivation v2 receipt base and replay barrier

`NpcMotivationState` v2 adds `ReceiptBaseRevision`. `AcceptedUpdates` must be contiguous from `ReceiptBaseRevision + 1` through `Revision`; its count equals `Revision - ReceiptBaseRevision` and never exceeds 256. A current row with `StateRevision` below the base needs a compact, immutable **latest-row anchor** keyed by `(kind, row ID)`, containing its latest accepted state revision, evidence ID, owner, and (for goals) `GoalStartRevision`. Validate every current row against either its retained latest receipt or this exact anchor. Also reject any retained receipt for the same row with a revision later than that row/anchor. This preserves schema 46's latest-row anti-rewind rule: an older valid goal lifetime cannot replace the latest row. Separately retain a **goal-origin anchor** keyed by `(goal ID, GoalStartRevision)` only for a current goal generation or a retained task reference. This is a compressed copy of the actual accepted origin receipt and must preserve `GoalGenerationOrigin=true`, `GoalStartRevision==Revision`, owner, applied time, and source evidence. A continuation receipt with a matching start number is never an origin. Migrate only from a fully validated schema-46 receipt; do not infer an origin from a current row. Do not rewrite `StateRevision` to a recent number solely to make the check pass. Current-row anchors are bounded by the bounded row sets; older goal-origin anchors are bounded by retained task references. On each update, replace its latest-row anchor; release an old origin only when neither a current goal nor a retained task references it.

The motivation update ticket remains bound to `WorldStateStore`, `bindingEpoch`, framework scope, owner, and expected revision. For v2, a caller must also obtain a one-use issuance token from that live store; the commit verifies the issued proposal ID, source identity, and expected revision, then consumes the token. Tokens do not survive restore, clone, or closing the dialogue. Native producers additionally verify their live source (vitals revision or active alarm episode) at admission. New operation IDs include a v2 save-local monotonic serial; the persisted next serial never decreases or wraps. Old v1 operation IDs remain in the migrated retained receipts for history but cannot be issued or accepted after migration. This **legacy namespace fence** is essential: retaining only 256 arbitrary operation strings cannot prove that an arbitrary older string was never used. A Bloom filter or bounded hash tombstone set would give a false or eventually incomplete answer, so neither is an authorization source.

Native safety uses `goal:native-safety` across incident episodes. Recovery reuses `goal:native-recovery` across injury episodes. Schema 46 now stores `(GoalId, GoalStartRevision)` in tasks and `GoalGenerationOrigin` in accepted receipts. A retained task pins that generation's exact origin receipt or compact origin anchor. Current goal state or its latest evidence ID cannot substitute for the start generation. On task eviction, release the pin only after no care, lodging, action, or other live owner references the task. Goal binding permits task admission only; task completion never fulfills the goal without its own native evidence.

## Task/action admission and history

For v2 admissions, issue a save-local monotonically increasing task/action serial from `WorldStateStore` and include it in the durable ID. Task-step action IDs remain `task.Id + ":step:" + index`. An issued capability binds scope, live store epoch, resident, proposal source, candidate digest, serial, and expiration; acceptance is one-use. Task and action acceptance verify the capability before native consent, schedule, inventory, and resource checks. Old arbitrary v1 IDs remain valid **for their already accepted rows only**. They can finish after migration, but no new v1-format proposal can enter the ledger. This avoids replay after the old row is evicted. `NpcHealthCare.MakeTaskId`, health-lodging booking/payment IDs, model offer IDs, and any ID parsers must be adapted to the new issued ID while preserving validation of existing v1 rows. A fresh ID is required for each new care attempt; a previous episode/revision cannot silently regenerate the same ID.

Prune a terminal task together with all its step actions only when no live task, care record, lodging booking, action transition, failure receipt, source-item dependency, or other save owner points at them. An undelivered task failure receipt pins the task until `TryDeliverNpcTaskFailureReceipt` commits the observation and marks delivery. A completed transfer action pins until its receipt is durably projected or otherwise accounted for; a completed interaction pins until its memory marker is set or a terminal ineligibility outcome is recorded. `ReturningToRoutine` and other unfinished transitions count as active even when the action phase is terminal. Completed treatment needs a bounded typed treatment outcome before deleting the action/purchase/task group, and that outcome must identify which exact receipt and native effect it was derived from. Keep the latest eight verified treatment outcomes per person (or another fixed small policy selected by tests). `NpcTreatmentRecall` can use those outcomes for recent exact facts; for older unavailable details, it must say evidence is unavailable, never infer a seller, price, or cause from aggregate data.

The source uses a deterministic rotating sweep over append-order candidates; the recent-window rank uses `UpdatedAt` then ordinal ID. Selection does not promise globally oldest-first eviction. A task group is atomic. The exact latest action per person stays pinned, so `LatestNpcAction` keeps its list-order meaning. Rebuild `npcTasksById`, `npcTasksByResident`, failure-receipt index, `npcActionsById`, and `npcActionsByResident` after any list replacement or restore. Reset transfer, interaction and treatment scan cursors when rows are removed. A prune transaction validates the complete proposed world copy, including all cross-ledger references, before publication. On failure, leave the old state unchanged and report pressure rather than dropping evidence.

The compact outcomes are not a second unbounded log. Each type has an explicit fixed per-person slot count and global bound. If a lasting fact needs more than that, move it to the owning domain ledger with its own bound and lifecycle before pruning. No action is removed merely because it is old.

## Source-specific admission cursors (required before pruning)

Fresh issuance prevents reuse of an old token, but it does not prevent a caller from minting a fresh token for the same source event. The smallest production source set is explicit:

* **Native health motivation:** `NpcHealthNeedLifecycle` derives operation IDs from `(need|goal, NpcVitalsView.Revision)`; `NpcVitals` persists a monotonic per-person vitals revision. Add two per-person `long` cursors, last accepted need vitals revision and last accepted goal vitals revision. At commit, reread the current vitals and require exact revision/value match and `sourceRevision > cursor` for that row kind. Advance the matching cursor in the same state mutation as the motivation receipt. Separate cursors allow a goal update to finish after a need update for the same vitals revision. Migrate each cursor from validated schema-46 accepted native-health operation/evidence IDs, not from the last 256 receipts after truncation. Reject malformed or contradictory recognized native-health IDs during migration. Current row evidence alone may omit older accepted revisions.
* **Native safety motivation:** `NpcNativeSafetyGoalLifecycle` uses an opaque digest of `(person, incident.Id, StartedAt)`, while `RecordHostileThreat` can reuse the same incident ID after expiry. A bounded digest set cannot protect unlimited episodes. Add a persisted monotonic `IncidentGenerationSerial` to `CivilianIncident`, allocated by `WorldStateStore.RecordHostileThreat` from a world counter on each new incident generation. Keep a per-person last-started safety serial. `start` requires the currently active incident object and serial greater than that cursor; update the cursor atomically with the accepted origin receipt. `fulfill`/`abandon` require the current active goal generation and its exact incident serial; terminal status closes that generation, and the start cursor prevents reopening it later. Migrate serials to retained incidents in deterministic `(StartedAt, Id)` order, then match any accepted start digest to a retained incident before setting its observer cursor. Historical incidents no longer present cannot be reintroduced through the legacy operation namespace. Counter overflow fails closed. A time-only cursor would reject legitimate different incidents sharing a game timestamp.
* **Conversation task or standalone action:** the current adapter creates a new `Guid` in `PeopleOfTheIliacBayMod.DialogueActions` and `GoalActions` just before acceptance. That random ID is not a durable source identity. Capture a save-local per-person command ordinal when the canonical user turn enters the action/goal pipeline; retain the ordinal and source context through asynchronous model/willingness callbacks. `WorldStateStore` issues at most one live capability for that `(person, ordinal, canonical turn digest, candidate digest, store epoch)`. Store last *accepted* command ordinal per person. Acceptance requires a newer ordinal and advances it with the task/action row. A rejected command need not consume the accepted cursor. Restore invalidates the live capability, so an old callback cannot request a new token; a newly submitted turn receives a new ordinal. This covers direct requests, semantic offers, goal actions, and `TryAcceptNpcDeparture`. Merely changing `proposalId` to another random value is insufficient.
* **Health-care task:** `TryAcceptAndBindNpcHealthCareTask` already prevalidates the care transition and publishes the task and acting row together. Bind its issuance to `(care episode ID, expected care revision)` and require that current row is still Seeking/eligible Blocked. The successful transition increments care revision and acts as the finite source cursor. Task-step actions use `(task ID, current step index, task revision)`; `TryDispatchNpcTaskStep` already checks these live values and derives the exact step action ID. They do not consume a conversation command ordinal.

`TryCommitNpcMotivationUpdate`, `TryAcceptNpcTask`, and `TryAcceptNpcAction` must reject unclassified direct v2 admissions. Tests may build fixtures through explicit fixture helpers; production cannot silently fall back to an arbitrary string ID. Legacy rows can continue, reconcile, and load, but no new legacy-source admission is permitted. The save-local ID serial and the source cursor serve different purposes: one gives unique durable row identity; the other prevents duplicate effects from a fresh ID.

## Exact dependency inventory for eviction

`NpcTaskStore.CopyNpcTasks` needs the task plus every dispatched step action; it validates completed effect IDs, acquired source items, targets, and active actions. `NpcHealthCare.CopyNpcHealthCareRecords` requires a task while Acting. `NpcHealthLodging.ValidHealthRestLodgingAuthority` currently parses a deterministic care task ID and requires the task even after a booking is made; a completed booking that remains saved would pin task history forever. Give a closed booking its own bounded native payment/stay proof, validate it in the lodging owner, and release the task only after the booking no longer drives active rest or payment. Keep active booking task/action rows exact. For v1 bookings, retain the old parser; for v2 bookings, validate the issued task ID and source binding. If the lodging owner cannot bound or expire closed bookings, report that as a separate storage blocker rather than evicting their tasks.

`NpcTreatmentRecall` scans tasks/actions and hashes their authority for read freshness. On terminal eviction, create the fixed-size verified treatment outcome before removal, include its revision in the authority signature, and return unknown for details older than that outcome window. `DrainNpcItemTransferReceipts` currently revisits completed actions and consults `NpcExperienceInbox.HasOutcome`; add a durable per-action projected marker set in the same saved mutation as a successful inbox enqueue. Pin unprojected receipts. `NpcInteractionMemory` already marks `InteractionMemoryRecorded`; pin eligible unmarked completed interactions. `ConversationActionReply`, `NpcFollowTransition`, `NpcRoutineRecoveryTransition`, `NpcHealthCareRecoveryHandoff`, inventory/item-source resolution, and failure-receipt delivery must continue to resolve their live IDs. `LatestNpcAction` cannot rely on list order after pruning. Rebuild action/task indexes and reset the transfer drain cursor when the retained lists change.

### Follow-up source audit: projection and booking pins

The current experience inbox is **not bounded**: `NpcExperienceInbox.CopyValidated` requires `Revision == Entries.Count` and retains every canonical event. Motivation receipt retention must not be described as bounded total save history. A transfer projection marker prepares action retirement; it does not implement inbox retention or autobiographical compaction.

Completed interaction actions also need an explicit unresolved-projection policy before general task/action eviction. `TryRecordNpcInteractionMemory` requires eligible live identities and a time before the action deadline. Its runtime caller additionally checks current physical proximity and visibility. Consequently, some completed interactions can become permanently unprojectable. Do not manufacture a late observation or merely mark them recorded to release a pin. A future typed disposition must distinguish recorded evidence from unavailable observation and preserve that distinction across restore.

Healthcare booking retirement must precede eviction of its linked task. The existing restore validator requires that task even for an expired booking. Cleanup may release only expired bookings with a validated terminal task, no care reference, no active or returning action, and no traveler/trip reference. Budget examined rows as well as removals; do not scan all inns every frame. That created a booking rejected by the healthcare restore validator. The implemented guard now accepts only an unchanged end time for these bookings. ## Save migration and branch behavior

Raise `WorldState.CurrentVersion` from 46 to 47. During load of an older save, first validate the original v1 motivation and existing task/action ledgers using their original rules. Existing pre-46 goal migration must run before this conversion. Deep-copy the candidate; migrate receipt base/anchors, assign the v2 serial high-water marks above all retained v2 values, and build retention metadata without mutating the input. Keep all live tasks/actions and their references. Do not opportunistically prune during this first migration. Validate the full candidate a second time under the new schema and publish it atomically; invalid source data still fails closed. `Snapshot()` and `Restore()` must take the same version-aware path, and restore must invalidate issuance capabilities through the existing `bindingEpoch` change. A save clone inherits durable counters and history but gets a new live epoch; branches may advance independently without accepting each other's in-memory capabilities. Scope ID alone is insufficient to distinguish cloned live owners.

Subsequent maintenance may prune in bounded batches after projection checks. Never delete a row from a save before its replacement outcome and all dependent validation are in the same committed snapshot. The memory archive is not this migration's storage sink. Keep backup/recovery behavior of the host save system; no destructive rewrite of existing player archives is part of this design.

## Recall and interaction prerequisites confirmed by source audit

`NpcTreatmentRecall` currently derives facts from terminal tasks/actions and their exact native treatment receipts. Purchase attribution additionally requires the matching purchase step, acquired UID, provider, chronology and paid amount. `NpcMemoryReadSnapshot` pins that detail through `TreatmentRecallAuthority`. Removing these rows without replacement would lose verified facts and change snapshot authority.

Before terminal eviction, introduce a bounded typed treatment-outcome summary per person. Validate the full dependency chain before publishing it; retain observed time, treatment kind, actual health delta and rest timing. Purchase attribution must distinguish verified purchase, no linked purchase, and unavailable evidence; only verified attribution carries provider and price. Summary revision and coverage metadata must invalidate stale reads. Overflow must produce an explicit unavailable-history result for older questions, never a claim that treatment did not happen. These summaries provide recall, not permission to replay treatment or payment.

Completed `Interact` rows need a separate Pending/Recorded/Unavailable projection disposition. Current runtime projection requires physical co-presence and visibility; a restored terminal action does not replay that observation. Missing historical proof must not fabricate a meeting. Publish both reciprocal source-keyed journal entries and Recorded together; transient failures remain Pending and pin the action. A definitive inability to verify the encounter may become Unavailable with a reason. This does not authorize journal deletion or autobiographical compaction.

Required tests include truthful recall before/after eviction and reload, exact purchase attribution after source-row eviction, future-time hiding, bounded-summary overflow, stale snapshot rejection, cross-person isolation, reciprocal interaction projection exactly once, and no invented encounter after missing physical proof. These are prerequisites, not implemented behavior in the schema-47 checkpoint.

## Alternatives rejected

Raising 4,096/1,000/10,000 postpones exhaustion. Trimming old rows without a new admission protocol permits replay and breaks exact references. Keeping every historical ID as a tombstone remains unbounded. Probabilistic tombstones can deny legitimate work and cannot establish exact authority. Sending operational receipts to autobiographical memory would mix effect authorization with narrative recall and conflicts with the deferred memory-compaction work.

Implementation should proceed only after the goal/task binding schema and the full incoming-reference inventory are reviewed together. In particular, `NpcHealthLodging` currently reconstructs health task IDs, so the v2 issued-ID format requires an explicit dual-version validator during migration.
