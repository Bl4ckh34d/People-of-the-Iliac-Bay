# Paired guard night patrols

The approved end state is two finite roster guards physically joining a surveyed circuit at night, carrying torches, answering crimes from their actual positions, and returning without teleportation. Existing posts, guard IDs, deaths, health, native surrender and saved crimes remain authoritative.

1. Add a serializable core patrol plan containing two identities, individually surveyed join routes, a closed circuit, walking speed/time scale, spacing and exact start/end times. Both members wait for a shared circuit start; the follower uses a shifted circuit entry. Derive positions from game time and support physical return to individual posts using only traversed circuit/join segments. Test joins, waiting, multiple laps, dawn return, explicit interruption, defensive copies and save reconstruction.
2. Persist plans in GuardRoster with transactional validation and migration defaults. Define patrol participation and interruption explicitly. Keep responses eligible from actual patrol positions; cached building approaches must join those positions through validated travel, and return must ultimately reach a real post. Test death, one unavailable partner, crime interruption and resumes without position jumps.
3. Survey valid circuits and both joins incrementally in the live exterior. Reject disconnected routes and formations that collide at sharp reversals; never invent straight paths. Keep guards posted when no usable circuit exists. Prefer a few short routes over expensive all-city routing.
4. Integrate night start/stop, paired walking animation and existing torch controls. Add a patrol toggle and bounded pair allocation while retaining stationary posts. Direct indoor loads reconstruct patrol progress from saved time; offscreen travel does not depend on actors.
5. Verify actual-player paired spacing, both moving sprites, night/day transition, crime travel from the current position, native surrender, pursuit/return, death/reload and no extra roster identities. Profile route work and visible actors. Wall patrols require separate wall navigation acceptance and remain part of M4.

Step 1 is a source foundation, not proof of a playable patrol. The installed0.3.23 preview remains authoritative until runtime steps and live verification pass. M4 and the overall goal remain open.

Step 1 implemented: `src/LivingCities.Core/PatrolPairPlan.cs`, `tests/LivingCities.Tests/PatrolPairTests.cs` and native validation in `tools/Editor/LivingCitiesBuild.cs`. Core208/208 pass. DFU's serializer preserves the standalone plan, exact phase at fractional absolute game timestamps and physical return. The circuit validator computes minimum separation over each linear interval between corner events and rejects circuits where separation falls below one metre; circuit count is bounded at512 points. This does not validate terrain clearance, simultaneous joining collisions or wall navigation, which require step3. Source-only validation uses `tools/VerifyGuards.ps1`; it stages source but does not replace the installed player bundle. Next is step2 roster persistence and interruption/response ownership.
