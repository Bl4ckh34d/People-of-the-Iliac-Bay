# Native service earnings and refund settlement

Status: Core settlement and native adapter/probe are installed in schema 52. Native controlled settlement passes, including real currency, exact rollback and serialization. Ordinary paid-companion gameplay remains unproven; see [acceptance and limits](2026-10-23-schema52-acceptance.md). The starting-point and source-checkpoint sections below record earlier states. Read with [service-health interruption](2026-10-23-service-health-interruption-plan.md) and [paid-service recovery design](2026-10-23-paid-service-recovery-design.md).

## Verified starting point

`NativeNpcServiceContractFunding.TryReserveFromPlayer` is the only native service-currency adapter. On the bound Unity main thread it validates a save-bound service write ticket, derives a detached reservation, captures the actual player's `GoldPieces` and exact letter-of-credit objects, UIDs, and values, debits through `PlayerEntity.DeductGoldAmount`, then commits one funding receipt. A rejected commit restores and verifies the exact player currency. Player and mod saves still have separate crash boundaries.

`NpcServiceContract` accounts for prepaid escrow, earned wages, releases, and refunds. `WorldStateStore.TryCommitNpcServiceContracts` can publish a directly derived contract ledger and exact new receipt evidence together, but cannot update NPC money. NPC cash is authoritative as `NpcInventoryState.WalletGold`; the live `NativeNpcInventoryOwner` carries native item objects, not a second cash purse. `CommitNpcInventoryTransaction` updates that wallet separately. Calling it before or after the service commit would permit money without contract settlement or a receipt without credited money. No native earnings or refund payout path currently exists.

## Minimal living-NPC settlement adapter

Add one trusted, synchronous `NativeNpcServiceContractSettlement` seam. Share funding's bound-main-thread and reentrancy guard. Never yield between the native currency change, Core publication, and any rollback. Model text and public receipt factories do not prove a transfer.

1. Read actual native time from `DaggerfallUnity.Instance.WorldTime.Now.ToSeconds()`. Require the current `GameManager.Instance.PlayerEntity`, exact payer ID, current store/branch/epoch/ledger ticket, contract ID and revision, allowed status and end reason, and unused receipt IDs. Capture the NPC inventory revision and saved wallet. If the inventory has not been materialized, use `NativeNpcInventoryBridge.TryOpen` with its existing deterministic starting-wallet policy **before** capturing transaction tickets; then re-read both revisions. Do not issue new starting gold on retries. Reject wallet or player-currency overflow before touching currency.
2. Use the pure contract transition to derive a detached `TryReleaseEarnings` or `TrySettle` result and `NpcServiceContractLedger.TryReplace` candidate. Use the contract's calculated unpaid earned amount and unused escrow; do not duplicate the rounding formula in native code. Construct an earnings receipt only for a positive wage, with `contract:<id>:escrow` as source and the exact NPC ID as destination. Construct a refund receipt only for a positive refund, with the same escrow source and `player` as destination. Zero amount requires a null receipt. Receipt `GameTime` is the actual native transfer time, never a backdated expiry time. The planned late-expiry pure transition must keep effective accrual end at `BlockEndAt` while allowing a later actual transfer time.
3. Add a narrow `WorldStateStore` commit that validates the existing service ticket, directly derived ledger, new exact receipt evidence, NPC inventory owner/revision, unchanged item payloads, and wallet delta equal to the new earnings receipt. Prepare detached service state, evidence state, and wallet-only inventory replacement before any publish. Publish all three within one non-failing store mutation, and invalidate the inventory index in that mutation. Preserve the inventory transaction ID/revision and existing UID ownership invariants. For zero earnings, leave the NPC inventory untouched. Existing `TryCommitNpcServiceContracts` and `CommitNpcInventoryTransaction` must not be chained as a substitute.
4. For a positive refund, snapshot the real player's `GoldPieces`, combined `GetGoldAmount()`, and each letter-of-credit object, UID, and value. Credit checked `GoldPieces` and verify the exact increase before calling the combined Core commit. Letters of credit need not change when refunding coins, but must remain exact. If pre-publication or Core commit fails, restore and verify the full snapshot; report rollback failure distinctly and do not retry blindly. A successful Core commit has no fallible follow-up. Earnings-only release needs no player-currency mutation, but the Core wallet credit and service receipt must still publish together.

The receipt registry is saved evidence of a native adapter's completed transfer, not an independent currency source. This synchronous rollback covers ordinary rejection and exceptions. It cannot make DFU player saves and mod saves crash-atomic; any stronger guarantee needs a separate durable recovery protocol and native acceptance proof.

## Death and estate remain open

`NpcServiceContract.TrySettle` accepts a death `settlementRecipientId`, but the current native adapter has no proven estate destination. A death payout must bind a canonical estate ID to a persistent, uncleared corpse incident and verify `WorldStateStore.CorpseInventoryOwner(incidentId) == contract.NpcId`. The saved dead-NPC wallet could later materialize into corpse gold through `NativeNpcInventoryBridge.TryMaterializeCorpseWallet`, but an open corpse inventory has its own live item collection. That collection must be closed and captured or updated under the same exact transaction discipline. A cleared or missing corpse cannot receive an asserted payment. Until this owner mapping and live-container handling exist, reject death settlement and keep escrow pending; do not route it to an arbitrary ID or silently credit a dead NPC wallet.

Renewal combines prior earnings, refund, and new player funding in one transition. It needs its own multi-transfer native transaction and is outside the minimal expiry/cancellation payout seam. The runtime must not renew or mark a contract settled when a required transfer is unavailable.

## Focused tests and native acceptance

Start with failing Core tests for one combined ledger/evidence/wallet publication, stale inventory or service ticket rejection, exact receipt matching, zero-amount null receipts, wallet cap, replay, and no partial mutation. Test expiry observed after `BlockEndAt` with fixed earned time and actual later receipt time. Keep pure accounting invariant `FundedGold = ReleasedGold + RefundedGold + EscrowGold`.

Extend the native persistence probe with a real mixed coin/letter-of-credit funding fixture and a controlled contract that earns half its 120-gold period before a health-owned suspension. At settlement, require exactly 60 gold added to the saved NPC wallet and 60 refunded to the actual player, escrow zero, exact distinct receipts, and the same facts after a real save/reload. Inject a post-credit Core refusal: verify player coins, combined gold, exact LOC objects/UIDs/values, NPC wallet, contract ledger, and evidence registry all return to their pre-attempt state. Reject a foreign or stale ticket, duplicate receipt, overflow, and death without proved estate ownership. This probe must inspect native currency as well as saved accounting; a Core-only passing test is insufficient.

## Native source checkpoint

`NativeNpcServiceContractSettlement.cs` now shares the funding adapter's main-thread transfer guard. It derives dues through the pure contract, credits a real player refund before the combined Core commit, and restores exact native currency on rejection. A failed rollback returns an aggregate exception; callers must not retry that failure automatically. Death settlement remains unsupported pending estate ownership.

`NpcServiceSettlementNativeProbe.cs` is wired into the framework probe. Its disposable fixture exercises mixed coins/letters of credit, half-period health suspension, late expiry, forced post-refund rejection and FullSerializer restoration. Nested cleanup restores the native clock even if currency cleanup fails; the PASS marker follows cleanup. Runtime compilation passes, but this source checkpoint does not establish native execution, gameplay recruitment, or installed schema-52 acceptance. The installed accepted package remains schema 51 until the integrated build and native tests pass.
