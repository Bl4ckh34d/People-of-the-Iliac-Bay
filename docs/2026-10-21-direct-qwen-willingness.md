## Implemented boundary

The existing complete-goal path can now use a separate Qwen willingness call when `Dialogue.EnableDecisionPlanner` is off and both `-peopleoftheiliacbay-goal-extraction` and `-peopleoftheiliacbay-qwen-willingness` are explicitly present. This is an opt-in integration experiment, not a new default or model placement change. The regular launcher has not been changed to enable these experimental flags.

`LocalQwenWillingness` reuses the same captured `NpcDecisionRequest` as D3: exact current text, attributed history, bounded memory/context and immutable ordered proposal. The model returns only ACCEPT or DECLINE through a bounded grammar and strict parser. Data is JSON-escaped; this does not prove semantic correctness or resistance to every prompt injection. Unknown/malformed/unavailable output confirms no agreement.

The Qwen call owns a separate native stage token. Completion rechecks module/settings, session, actor and snapshot; consumed/stale callbacks cannot accept again. Existing proposal signatures, fresh target/resource preparation, native consent and atomic Core task/action acceptance remain mandatory. Extraction alone never means agreement. Pending offers still route before extraction; active commitments retain their cancellation/interpretation path.

A review found an existing D3-unavailable bypass: when no D3 willingness session existed, the legacy single/decomposition path could set `required:false` and directly accept Qwen's combined interpretation. Native139 reproduces one acceptance callback at that resolver boundary. Checkpoint140 closes it centrally when the planner is configured, and rejects new inactive requests early without changing offer/commitment precedence. A configured D3 outage never silently enables the new Qwen consent backend. The controlled outage probe does not exercise a full user-text outage route; it directly tests that resolver with text replies disabled.
