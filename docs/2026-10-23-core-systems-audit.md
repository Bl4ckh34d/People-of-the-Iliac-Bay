## Working foundations

- `NpcMotivationState.cs` stores sparse, owner-bound needs, goals, priorities, evidence, revisions and accepted-update receipts. `NpcMotivationStore.cs` requires an owner/scope/epoch/revision ticket and publishes each validated **single-row** update at one assignment. Context capture includes transient capability, resource, threat and duty constraints; those transient facts are not persisted as action authority (`NpcMotivationContext.cs`, `NpcMotivationStore.cs`).
- `NpcHealthNeedLifecycle.cs` maps observed saved vitals to a health need and recovery goal, updates only when values change, and closes/reopens recovery after healing or a new injury. `NpcNativeSafetyGoalLifecycle.cs` records a directly witnessed threat and fulfills or abandons its safety goal from native episode evidence. These are specific producers, not a common lifecycle.
- `NpcTasks.cs` and `NpcTaskStore.cs` validate bounded typed steps, exact item dependencies, one active task per resident, action dispatch, completed effect IDs, failure receipts and save/restore bindings. `NpcHealthCare.cs` persists a separate care episode with seeking, acting, blocked/retry and recovered phases. `StreetPopulation.HealthCare.cs` chooses a currently available care task and uses the existing task executor. It reconciles effects and retries or replans after failure.

## Blocking seams

1. **No shared need-to-task arbitration.** Health care starts when observed health is at or below 75%, using `ShouldInterruptWork` and `TryBeginNpcHealthCare`; candidate scoring then chooses rest, an owned potion, a Guild potion or a shop purchase (`NpcHealthNeedLifecycle.cs`, `NpcHealthCare.cs`, `StreetPopulation.HealthCare.cs`). The recorded recovery goal's priority is not read by this selection path. Safety goal is likewise an observation record; native alarm behavior owns the actual response (`CivilianResponses.cs`, `StreetPopulation.cs`). `NpcTaskPlan` has no goal or need identity (`NpcTasks.cs:18-29`). No common code selects among active goals, current duties, native protections, urgency, capabilities, resources and an occupied task. Adding another need as another independent overlay would multiply conflict rules.
2. **Lifecycle ownership is split.** Motivation goal status, care episode phase, task phase, action effect and actual vitals live in separate records. Health runtime explicitly cancels an incompatible task, binds a new one, reconciles terminal actions, then blocks or completes care (`StreetPopulation.HealthCare.cs:67-145`). A reusable lifecycle needs one owner of the transition policy: observe native state, compare competing goals, admit a feasible task, confirm its effect, and re-evaluate the original need. Existing ledgers should remain authoritative for their own facts; a planner must not infer treatment or goal fulfillment merely from task acceptance.
3. **Paired health updates lack an atomic group.** An injury or healing can require both need and goal changes. `NpcHealthNeedLifecycle.Observe` commits the need first, rereads state, then commits the goal; if the second commit fails, it returns success for the first (`NpcHealthNeedLifecycle.cs:53-65`). `TryCommitNpcMotivationUpdate` guarantees atomicity for one row only (`NpcMotivationStore.cs:43-77`). The precheck reserves two available revisions, and no failing second step was demonstrated in this audit's single-threaded current path. Thus this is a transaction boundary to test and repair when the common lifecycle can interleave or fault; it is not evidence of a currently reproduced partial save.
4. **Persistent ledgers have lifetime ceilings.** `NpcMotivationState.MaxAcceptedUpdates` is 4096 **per person**. Validation requires receipt count equal to the absolute revision and receipts numbered from 1; `TryApply` rejects further writes once revision reaches 4096 (`NpcMotivationState.cs:208-227,233-244,259-269`). Health and safety producers also stop at this cap. A living resident can therefore permanently lose further need/goal updates after enough distinct episodes. Separately, `TryAcceptNpcTask` rejects the 1001st saved task globally, and action acceptance rejects the 10001st saved action (`NpcTaskStore.cs:97-109,173-183`; `NpcActions.cs:377,512`). These are lifetime limits, not active-work budgets. Trimming receipt lists alone would break revision validation and replay protection; any bounded retention requires a versioned migration and a durable deduplication policy across save branches.
5. **Capabilities and resources exist as context types, not a common feasibility gate.** `NpcMotivationContext.cs:191-224,263-301` defines source-bound constraints. Current health task construction checks native inventory, money, item effectiveness, routes and beds in its adapter, which is good. A shared selector must consume fresh, typed feasibility results and recheck them at task admission/dispatch. Unknown constraints must not become available by default, and neither model text nor a goal may mint stock, money, skills or access.

## Smallest next sequence

1. Define one narrow arbitration contract over current motivation view, duties, native priority rules, active task and fresh feasibility results. Pilot it with existing health and safety inputs. Preserve quest protection and native alarm authority. Return a selected goal plus a reason to keep, interrupt or defer the current task; do not add new autonomous need producers yet. Verify conflicting health/safety/work cases and save/reload determinism.
2. Add an explicit goal/task association and a single reconciliation call for confirmed task effects, failure, interruption and changed native need. Reuse `NpcTaskStore`'s effect receipts and `NpcHealthCare`'s retry policy. Verify that accepted or failed treatment never counts as healing without a native vitals change.
3. Make correlated need/goal publication atomic if the pilot exposes interleaving or injected second-step failure. Specify receipt/revision semantics first, then add rollback, replay and serialization tests. Do not silently change existing receipt history.
4. Design bounded durable motivation/task/action history together. Keep active rows and open commitments; prove old-save migration, exact replay suppression, branch behavior and multi-year simulation before removing lifetime caps. The current 4096/1000/10000 limits remain blockers until this is verified.
5. Only then add further need producers and capability/resource adapters. Each producer supplies native observations; the common arbiter selects feasible work; the existing action executor confirms effects; reconciliation decides whether the need changed.
